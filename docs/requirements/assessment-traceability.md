# Assessment Requirements Traceability

## 1. Purpose and scope

This document maps the assessment requirements to existing project documentation, identifies design and implementation gaps, and defines the evidence required to verify each requirement.

Traceability covers the relationship between requirements, design decisions, implementation artifacts, tests, and demonstration evidence. Design documentation establishes intended behavior; implementation and verification records establish what has been built and demonstrated.

## 2. Status definitions

| Status      | Definition                                                                                                |
| ----------- | --------------------------------------------------------------------------------------------------------- |
| Documented  | Relevant design or research documentation exists; implementation and verification may remain outstanding. |
| Partial     | Some aspects of the requirement are covered, but the full requirement is not yet addressed or evidenced.  |
| Not started | No sufficient requirement-specific design, implementation, or verification evidence has been identified.  |
| Unverified  | Implementation or a claimed result exists, but adequate verification evidence has not been established.   |
| Verified    | Recorded evidence demonstrates that the requirement is satisfied within the stated environment and scope. |

The statuses in this audit reflect the project documentation and confirmed repository state at the time of review. No requirement is considered verified solely on the basis of a proposed design.

## 10. Traceability and verification criteria

Each requirement is associated with its design coverage, implementation artifacts, and verification evidence as those artifacts become available.

Verification records identify the relevant test or measurement, execution environment, expected behavior, observed result, and evidence location. Simulated results establish behavior only within the simulation's scope and do not independently establish behavior on physical devices, carrier networks, or production infrastructure.

A requirement's status reflects the strongest evidence available for its stated scope. Proposed behavior, implementation presence, and successful verification are distinct states.

## 11. Unresolved design decisions

| Decision area           | Unresolved question                                                                                                                          |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Integrated architecture | What are the component boundaries and communication contracts among the backend, phone, smartwatch, relay, and transaction-execution system? |
| Transport               | Will the demonstration use a simulated transport, a real WebSocket, or both?                                                                 |
| Timeout learning        | What sample-qualification rules, estimator parameters, and fallback behavior will be used?                                                   |
| Heartbeat liveness      | What response deadline applies, and what evidence is sufficient to declare a connection dead?                                                |
| Reconnection            | What retry limits, backoff bounds, network-quality classifications, and reset rules apply?                                                   |
| Outbox                  | What storage, retention, acknowledgment, replay, and terminal-failure policies apply?                                                        |
| Transaction contract    | What are the acknowledgment milestones, and how are delivery, acceptance, execution, and final outcome represented separately?               |
| Phone-to-watch relay    | What is the relay contract, and how is BLE liveness kept separate from backend liveness?                                                     |
| Diagnostic environments | Which devices, operating-system versions, network conditions, and process-interruption mechanisms are available for reproducible diagnosis?  |
| Capacity analysis       | Which workload assumptions, traffic models, resource estimates, and measurements support the 500,000-user target?                            |

These decisions remain open until supported by a documented rationale and, where applicable, research, calculations, or experimental evidence.

## 12. Current assessment status

Research and proposed designs exist for backend event publication, backend-to-phone event delivery, and adaptive connection management.

The integrated architecture, complete transaction lifecycle, diagnostic investigations and recorded results, remaining architectural trade-offs, capacity analysis, TypeScript implementation, automated tests, and reproducible demonstration remain outstanding or require verification.

No implementation, test result, device behavior, or capacity target is treated as verified without evidence appropriate to the relevant requirement and test scope.
